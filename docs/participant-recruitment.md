# Recruiting real test users and running ethical research

[← Resource home](../README.md) · [Release gate](release-readiness.md) · [Testing templates](../templates/README.md)

## For whom

Founders validating a product with the actual people it is designed for.

## The failure you are trying to prevent

Product quality is about actual user outcomes, not only whether a build compiles. Verify a realistic journey and the ways it can fail, then retest after changes.

## Common mistakes

- Counting other founders as independent target users
- Recruiting demographics by stereotypes rather than real use cases
- Over-incentivizing a positive review or answer
- Saving participant identity in public GitHub issues
- Treating five sessions as representative quantitative proof

## Run this test plan

1. **Define behavior and context based eligibility, not demographic assumptions.** Record version/environment, starting state, expected result, actual observation, impact, owner and retest outcome.
2. **Screen recruitment against actual task experience.** Record version/environment, starting state, expected result, actual observation, impact, owner and retest outcome.
3. **Separate voluntary consent from marketing outreach and recordings.** Record version/environment, starting state, expected result, actual observation, impact, owner and retest outcome.
4. **Offer accessible formats and compensation as appropriate.** Record version/environment, starting state, expected result, actual observation, impact, owner and retest outcome.
5. **Run neutral session; tag unassisted task outcomes.** Record version/environment, starting state, expected result, actual observation, impact, owner and retest outcome.
6. **Retest with matched participants and disclose research limits.** Record version/environment, starting state, expected result, actual observation, impact, owner and retest outcome.

## Working method

**Prepare:** select three high-risk tasks and a realistic device, account and permission profile. Use fictional data; do not disclose user recordings, credentials or restricted company information.

**Observe:** run both successful and failure/recovery paths. Distinguish a user's observed behavior from the researcher's proposed solution.

**Prioritize:** flag data loss, harm, exposed private information and blocked primary user actions before cosmetic problems. Record any accepted risk with an accountable owner.

**Verify:** deploy a versioned fix, repeat the same task under comparable conditions and record improved/unchanged/worse/pending outcome.

## Completion evidence

Screening criteria, neutral tasks, consent plan, anonymized observation table and evidence limitations.

## Don't overclaim

A single pass does not prove all users, devices, jurisdictions or failure conditions are covered. Tool limits and external rules evolve. Recheck official sources before a regulated or commercially consequential release.
